# 連携マッピング表 — keikaku-soudan との並走共有と全面引き継ぎ

- 作成: 2026-08-13 ／ 正典: PLAN.md §9-3・AGENTS.md §8
- 相手方: `oya-inai-keikaku-soudan`（相談支援専門員が一人称の姉妹版 Vault）
- **二つの Vault は時系列で交代するのではなく、重なって並走します。** 子が障害福祉サービス（児発・放デイ等）を使い始めたときから、親は本 Vault を、相談支援専門員は姉妹版を運用し、同じ本人を両側から記録します。この表は、その日常の共有（§2）と、親が関われなくなったときの全面引き継ぎ（§3)の両方を定義します

## 1. 互換キー — 何が共通だから繋がるのか

| キー | 内容 | 守るべきこと |
|------|------|--------------|
| `person_id` | `P_001` 形式。両 Vault で**同一人物に同一 ID** | 連携開始時に相談支援専門員と ID を突き合わせて固定する。以後変更しない（AGENTS.md ガードレール10) |
| `source_hash` | 原本の sha256。同一原本の突き合わせ | 同じ書類（会議録・計画の写し等）が両側に入るとき、二重記録をここで検出する |
| 共通フロントマター | type / created / sources / sensitivity / share_scope / provided_by 等 | 姉妹版と同一仕様（共通の宣言は schema-common.md §A、本 Vault の語彙は schema.md §1）。本 Vault 独自の追加は `lifestage` のみ |
| 継承12型の型ID | person / trial / protocol / trigger / concept / entity / ecomap / sensitive / public-system / procedure / query / review | ID は両 Vault で不変。対訳（人が読む面のことば）だけが違う——本 Vault の trigger は「きっかけ」、姉妹版は「引き金」。confirmed_by の「親が確認」は姉妹版の「家族に確認」と互換 |

**共有の範囲は機械が守ります**: 外に渡してよい一覧は `python3 scripts/okf_lint.py --allowlist` が出します（fail-closed）。`share_scope: origin-only` のページ——特に日記の「おもったこと」欄由来の記述——は、**どんな共有にも決して含まれません**。

## 2. 並走期の日常共有（主たる運用）

### 2-1 親 → 相談支援専門員

共有は計画相談の節目に限りません。姉妹版は受付箱＋チャットで日々の情報を常時受け取る設計なので、**チャット1本・メモ1枚の共有も日常の運用**です。

| 本 Vault 側（渡すもの） | 姉妹版側（落ちる先） | 備考 |
|--------------------------|----------------------|------|
| **意思決定支援ブリーフ**（こえ＋直近の せんたく＋関連手順書を AI が1枚に編んだもの） | raw/10_本人・家族から → あちらの ingest に乗る | 計画作成・モニタリング・担当者会議の前に渡すのが効果的 |
| せんたく・こえ の抜粋 | 同上。plan「本人の意向」欄の**証拠**になる | outcome:「通らなかった」の記録は意思決定支援の再検討素材としてそのまま価値を持つ |
| 親が気づいた変化のメモ | 同上 | 様式化しない。1行でよい |

### 2-2 相談支援専門員 → 親

| 受け取るもの | 本 Vault 側（落ちる先） | その後 |
|--------------|--------------------------|--------|
| サービス等利用計画・モニタリング報告の写し | `raw/70_会議・面談/`（受付箱経由） | 定期 ingest が内容を ふしめ・せんたく・手順書 等に編む |
| サービス担当者会議の記録 | `raw/70_会議・面談/` | 同上 |
| 事業所からの支援記録・報告 | `raw/30_事業所から/` | 同上 |

どちらの向きでも、同じ原本が両 Vault に存在しうるため、`source_hash` で突き合わせて二重に編まないようにします。

## 3. 全面引き継ぎ（親が関われなくなったとき）

並走が続いていれば、引き継ぎは新しい移行作業ではなく**共有範囲を広げる操作**です。これが並走設計の狙いです——親なき（亡きではない）が始まった日に、相談支援専門員の手元には既に本人の暗黙知の背骨があります。

### 3-1 型の対応表

| 本 Vault | 姉妹版での受け皿 | 変換の要点 |
|----------|------------------|------------|
| **koe（こえ）** | person の「人格の核」「意思表明のスタイル」＋関連 protocol 群 | バイブルの心臓を最初に渡す。evidence リンク（せんたく・ためしたこと）ごと渡す |
| **sentaku（せんたく）** | 意思決定支援の素材: plan「本人の意向」欄の証拠、または trial への読み替え | 「通らなかった」＋override_reason は、意思と異なる判断の記録としてそのまま引き継ぐ |
| **fushime（ふしめ）** | plan「この計画にした理由」相当の判断過程 | 当時何を比べ・何を諦め・本人がどう関わったかが、将来の計画の根拠になる |
| trial / protocol / trigger / sensitive / ecomap / entity / concept ほか継承12型 | **同型のまま移送** | 型ID・フロントマター互換のため変換不要。対訳の違い（きっかけ／引き金）のみ |
| **日記（raw/10_日記/）** | raw/10_本人・家族から/ へ**原本移送** | append-only を保ったまま移す。**「おもったこと」欄の扱いだけは本人・家族の意思で決める**（全部渡す／事実欄のみ／渡さない） |
| plan / monitoring / meeting | （本 Vault に存在しない） | 正本は最初から姉妹版側。引き継ぎ対象外 |

### 3-2 引き継ぎの手順（AI と行う）

1. 本人（可能な限り）・家族で、**「おもったこと」欄と origin-only ページの扱い**を決める（既定は渡さない）
2. AI に「全面引き継ぎの準備。allowlist を出して」と頼み、渡る範囲を機械的に確認する
3. §3-1 の表に従い、wiki は同型移送＋3新型の変換、raw は原本移送
4. 移送後、受け取り側の lint（姉妹版にも同じ検査があります）で健全性を確認する
5. 本 Vault 側に、引き継ぎの事実を ふしめ として記録する

## 4. 相談支援専門員がいない場合

相談支援が付いていない期間も、本 Vault は単独で完結します（それが既定です）。将来サービス利用が始まって相談支援専門員が付いたら、§1 の person_id 突き合わせから始めてください。姉妹版を使っていない専門職に渡す場合は、`docs/意思決定支援者のための読み方.md` を意思決定支援ブリーフに添えるだけでも機能します。
